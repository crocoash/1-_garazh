# Работа с этой конфигурацией

## Что это за папка

Результат «Выгрузка конфигурации в файлы» из Конфигуратора, а не исходники проекта.

| | |
|---|---|
| Конфигурация | УправлениеТорговлейДляУкраины **2.3.17.1** |
| Режим совместимости | 8.2.13, интерфейс — 8.2 |

Дерево: `CommonModules/`, `Documents/`, `Catalogs/`, `InformationRegisters/`, … Модули — текстом (`Ext/Module.bsl`, `Ext/ObjectModule.bsl`), метаданные — XML, формы — либо `Form.xml` (управляемые), либо бинарный `Form.bin` (обычные). Из-за режима 8.2 большинство форм здесь — обычные, то есть `Form.bin`.

## База и Конфигуратор — на другой машине

**Здесь только файлы выгрузки. Ни базы, ни Конфигуратора на этом компьютере нет.**

Перенос идёт **через GitHub**: `git@github.com:crocoash/1-_garazh.git`, ветка `main`. Здесь коммит
и push, на машине с 1С — `git pull` и загрузка конфигурации из файлов. Обратная выгрузка из
Конфигуратора едет тем же путём в обратную сторону.

Что из этого следует:

* Между «я правлю файл» и «правка в базе» есть **два лишних шага — push отсюда и pull там**.
  Push делает `snapshot.ps1`; правка существует только на этом диске, пока не отправлена.
* **Заливать всегда — это часть задачи, а не отдельная просьба.** Не спрашивать разрешения на push:
  пока коммит не на `origin`, на машине с 1С правок нет. Если коммит делался в обход скрипта —
  пушить руками и проверять, что `git status -sb` больше не показывает `ahead`.
* Проверить результат в базе я не могу в принципе: ни запустить Конфигуратор, ни синтаксически
  проверить модуль, ни посмотреть, что реально загрузилось. Всё, что я говорю о поведении в базе, —
  вывод из кода, а не наблюдение. Проговаривать это, а не выдавать за факт.
* Эта папка **всегда может отставать от базы**: пользователь мог доработать в Конфигураторе у себя
  и ещё не выгрузить сюда. В начале работы — `git fetch` и посмотреть, не появилось ли на
  `origin/main` новой выгрузки.
* **Штрихкоды чинить обязательно здесь, до push** (см. ниже). На той машине заливка в базу калечит
  объекты в макетах необратимо.

## Рабочий цикл и главный риск

Цикл доставки правок **двусторонний** — это главное, что нужно понимать:

1. Claude правит файлы выгрузки, прогоняет fix→check штрихкодов, делает снимок и **push**.
2. На машине с 1С — `git pull`.
3. Пользователь: Конфигуратор → «Загрузить конфигурацию из файлов» → «Обновление конфигурации базы данных».
4. Иногда пользователь сам дорабатывает в Конфигураторе и выгружает конфигурацию **обратно поверх
   папки**, коммитит и пушит; сюда это приезжает по `git pull`.

**Шаг 4 — источник тихих потерь.** Любая правка файла, не доехавшая до базы до того, как пользователь выгрузит поверх папки, исчезает без единой ошибки. Ловили дважды на разных типах правок:

* структурная (новый реквизит документа) — пропала и из файла, и из БД; вылезло только в рантайме «Поле не найдено…»;
* обычная (процедура в общем модуле + регистрация объекта в `Configuration.xml`).

Добавление реквизита файлом само по себе ничего не гарантирует, пока пользователь явно не принял структурные изменения в базе. Просто «загрузить из файлов» может быть недостаточно, если следующим шагом идёт выгрузка из БД обратно.

### Протокол

* **Перед правкой любого файла — прочитать его текущее содержимое.** Пользователь мог перезаписать своей версией. Не полагаться на то, что помню из прошлой сессии.
* **Перед тем как пользователь идёт в Конфигуратор дорабатывать своё — снимок** (`_tools/snapshot.ps1 "перед ручной доработкой"`).
* **После его выгрузки** — `git diff --stat` против той точки: сразу видно, что откатилось (только реально удалённые строки, без шума). Восстановление: `git checkout <точка> -- <файлы>`. Плюс руками вернуть регистрацию объекта в `Configuration.xml`, если пропала.
* **После добавления реквизита / перечисления / нового объекта** — явно напомнить применить изменения в базе.

## Штрихкоды в макетах — проверять ВСЕГДА перед сдачей работы

Штрихкод в печатных формах — не картинка, а **ActiveX-объект** внутри макета
(`<drawing><drawingType>Object</drawingType>` с блобом `<object xsi:type="xs:base64Binary">`
в `Template.xml`). «Выгрузка конфигурации в файлы» выборочно теряет этот блоб и/или имя рисунка
(`namedItem`), а обратная загрузка сносит объект и в базе — на месте штрихкода пустая рамка.
Обычные картинки (`drawingType=Picture`) не страдают.

В этой базе такой макет один: `CommonTemplates\Этикетка\Ext\Template.xml`, имя рисунка `Штрихкод`,
класс компоненты рабочий — V8.Barcod.2.

**Мой обязательный порядок (не пользователя — мой):**

```
1. Пользователь выгрузил конфигурацию в файлы / я закончил задачу
2. pwsh -NoProfile -File _tools/fix-barcodes.ps1 -Применить
3. pwsh -NoProfile -File _tools/check-barcodes.ps1
4. Отдавать работу и пушить ТОЛЬКО после «Все внедрённые объекты на месте»;
   результат писать в ответе
```

Само оно не восстанавливается: без шага 2 штрихкод сносит при каждой заливке. Подробный разбор
(два класса компоненты V8.Barcod.1/.2, ложные следы, грабли PowerShell) — `_tools/ШтрихкодыВМакетах.md`.

## Инструменты

* `_tools/snapshot.ps1 ["сообщение"]` — снимок: fix→check штрихкодов, `git add -A`, коммит со сводкой
  и **push**. Отдельно печатает список **удалённых** файлов: это главный признак молча потерянных
  правок. Запускать после каждой законченной задачи и каждой новой выгрузки из Конфигуратора.
  При неудачном push ругается красным и возвращает код 1.
  * **Что коммитить, указывается явно — без ключей скрипт останавливается с кодом 1.** Причина:
    в репозитории параллельно работает вторая сессия (вкладка), и `git add -A` забирает её
    недописанную правку в чужой коммит и отправляет на машину с 1С (ловили 05.08.2026 дважды).
  * `-Пути "CommonModules/X,Documents/Y.xml"` — коммитить только эти пути (через запятую одной
    строкой: при запуске через `-File` PowerShell массивы сам не разбирает). Изменённые файлы вне
    указанных путей печатаются списком «НЕ вошло в снимок» и остаются незакоммиченными.
  * `-Всё` — снимок всего дерева. Только после «Выгрузить конфигурацию в файлы», когда меняются
    тысячи файлов сразу.
  * Если в **корне репозитория** оказался второй комплект выгрузки (`Configuration.xml` +
    `CommonModules` + `Documents` рядом с папкой `Конфигурация`), скрипт останавливается с кодом 1:
    Конфигуратор выгрузил файлы не туда, и дубль уедет в git. Разобрать руками либо запустить
    с `-РазрешитьДубльВКорне`.
* `_tools/update-base.ps1` — **обратная сторона цикла, запускается на машине с 1С**: `git pull` →
  проверка штрихкодов → `DESIGNER /LoadConfigFromFiles` → `/UpdateDBCfg` → `/DumpCfg` в
  `.cf` на Рабочий стол (каждый раз поверх прежнего). Пользователь базы, пароль, строка
  соединения (`/S app1\garazh-cp`) и путь к `.cf` — блок настроек в начале скрипта; пароль
  лучше держать в `_tools/update-base.local.ps1` (он под `.gitignore` и подключается скриптом).
  Останавливается: на незакоммиченных изменениях перед pull (это может быть невыгруженная
  правка пользователя), на битом макете штрихкода **до** загрузки, на ненулевом коде возврата
  или слове «Ошибка» в логе Конфигуратора. Ключи: `-ТолькоЗагрузить`, `-БезPull`,
  `-ПропуститьПроверкуШтрихкодов`. Шаг `/UpdateDBCfg` требует монопольного доступа к базе.
  Запуск двойным щелчком — `_tools/update-base.cmd` (окно не закрывается по завершении);
  ярлык на Рабочий стол кладёт `_tools/make-shortcut.ps1` (один раз).
  Грабли, на которые уже наступили: `Start-Process` не экранирует аргументы — имя пользователя
  с пробелом уходит в 1С двумя аргументами и даёт «Користувач ІБ не ідентифікований»; git пишет
  нормальный вывод в stderr, и под Windows PowerShell при `$ErrorActionPreference = "Stop"` это
  роняет скрипт на **успешном** pull/push (обёртка `Гит` в обоих скриптах); git на машине с 1С
  живёт внутри клиента Fork (`%LOCALAPPDATA%\Fork\gitInstance\<версия>\cmd\git.exe`), в PATH его нет.
* `_tools/merge-cf.ps1` — объединение конфигурации базы с файлом `.cf` в пакетном режиме
  (`DESIGNER /MergeCfg <файл> -Settings <настройки>`). Перед объединением сам выгружает точку
  отката в `Рабочий стол\1c-до-объединения\`; к базе результат по умолчанию **не применяет** —
  сначала смотрят глазами в Конфигураторе (`-ПрименитьКБазе` применяет сразу).
  **Файл настроек объединения обязателен**: пакетный режим сам решений «чей объект берём»
  не принимает, а по умолчанию платформы молча берёт не ту сторону. Готовится один раз руками:
  Конфигурация → «Сравнить, объединить с конфигурацией из файла…» → флажки → Действия →
  «Сохранить настройки объединения в файл…», сохранить как `_tools/merge-settings.txt`.
  Расширение `.txt` намеренно — `.xml` внутри дерева выгрузки ломает загрузку конфигурации
  из файлов (та же ловушка, что с эталоном штрихкода).
* `_tools/fix-barcodes.ps1 -Применить`, `_tools/check-barcodes.ps1` — восстановление и проверка
  ActiveX-объектов в макетах; `_tools/barcode-object.txt` — эталонный блоб (расширение не `.xml`
  намеренно, см. ловушку ниже).
* Скрипты писались под Windows PowerShell 5.1 и работают в обеих средах: на macOS через `pwsh`
  (`brew install powershell`), на машине с 1С — через `powershell`. `snapshot.ps1` сам определяет
  интерпретатор и путь к `git` (`C:\Program Files\Git\cmd\git.exe`, иначе из PATH).
* `/_tools/*` в `.gitignore`, но пять файлов выше — исключения: они должны уезжать вместе
  с конфигурацией на машину с 1С. Тяжёлое (portable MinGit, BSL Language Server) по-прежнему
  не коммитим.
* BSL Language Server — на машине с 1С `_tools\bsl-ls\bsl-language-server\bsl-language-server.exe`
  (1.0.6 со встроенной Java, системная 8 не годится). Прогон: скопировать проверяемые `.bsl`
  в отдельную папку, `--analyze --srcDir <папка> --reporter json --outputDir <папка>`, смотреть
  только Error и только по своим файлам. Шумовые коды в этой базе: `InvalidCharacterInFile`
  (длинное тире в комментариях), `MissingCodeTryCatchEx` (пустые `Исключение` — идиома этой
  конфигурации), `DeprecatedCurrentDate` (`ТекущаяДатаСеанса` тут не используют — режим 8.2).
  Полезные: `TimeoutsInExternalResources` и всё про несуществующие методы.
* Репозиторий настроен с `core.autocrlf=false`, `core.safecrlf=false` и `.gitattributes` с `* -text` —
  git не трогает содержимое файлов выгрузки ни при каких обстоятельствах. Это **отличается** от
  `1--cvetkov`, где EOL нормализуются; здесь трогать настройку не нужно.

`CLAUDE.md`, `.gitignore`, `.gitattributes` закоммичены — если выгрузка из Конфигуратора их снесёт, восстанавливаются из git.

## Правка бинарных форм (Form.bin)

Обычные формы выгружаются бинарём, но **модуль формы править по файлам можно** — проверено на предыдущем проекте, база принимает.

Формат: заголовок файла 16 байт (`ff ff ff 7f` | pageSize=0x200 | ver=2 | 0), далее блоки; заголовок блока — 31 байт ASCII `\r\n%08x %08x %08x \r\n` (docSize, pageSize, nextPageAddr; `0x7fffffff` = конца нет). Первый блок по адресу 16 — TOC, по 12 байт на элемент (int32 hdrAddr, dataAddr, `0x7fffffff`). Элементов два: `form` (описание в скобочном формате) и `module` (чистый текст модуля, UTF-8 с BOM). Заголовок элемента — 20 байт дат + имя в UTF-16LE.

Важное упрощение: TOC и большие документы (модуль на 100+ КБ) хранятся **одним блоком без чанкинга** — платформа не режет их по 0x200. Поэтому repack не требует разбиения на страницы: дописать новый блок в конец файла (`docSize = pageSize = длина контента`, `nextPageAddr = 0x7fffffff`) и точечно поправить 4 байта `dataAddr` нужного элемента TOC (offset = начало данных TOC + индекс×12 + 4), остальной файл не трогать. Round-trip (repack неизменного модуля → unpack → сравнение) даёт побайтовое совпадение — этим и проверяется скрипт перед реальной правкой.

`unpack1c.ps1` / `repack1c.ps1` пишутся в scratchpad и воссоздаются по этому описанию за пару минут — в репозитории их держать не нужно.

**Границы:** модуль формы — можно; типы колонок таблиц значений и элементы формы (скобочная часть `form`) руками не менять, это делает пользователь в Конфигураторе. Каждый repack оставляет старый блок «сиротой» — файл растёт, самоисправляется при следующей настоящей выгрузке.

### Новые формы делать управляемыми — их можно писать текстом

В `Configuration.xml`: `DefaultRunMode = OrdinaryApplication`, но **`UseManagedFormInOrdinaryApplication = true`** — управляемые формы в этой базе открываются из обычного приложения. В конфигурации их уже 9 против 1479 обычных, в том числе у обработки (`DataProcessors/ComОбменУпрФормаУТП_УТ/Forms/ФормаУпр`) — образец для копирования.

Практический вывод: **новую форму не надо просить нарисовать в Конфигураторе.** Управляемая форма — это три текстовых файла:

```
<Объект>/Forms/<Имя>.xml              — дескриптор, FormType = Managed, свой uuid
<Объект>/Forms/<Имя>/Ext/Form.xml     — содержимое: AutoCommandBar, ChildItems, Attributes, Commands
<Объект>/Forms/<Имя>/Ext/Form/Module.bsl — модуль с директивами &НаКлиенте / &НаСервере
```

Плюс в XML объекта: `<Form>Имя</Form>` в конец `ChildObjects` (после `TabularSection`) и `<DefaultForm>DataProcessor.<Объект>.Form.<Имя></DefaultForm>`.

Порядок элементов внутри `<Form>`: `AutoCommandBar`, `ChildItems`, `Attributes`, `Commands`. Главный реквизит — `<Attribute name="Объект">` с `<MainAttribute>true</MainAttribute>` и типом `cfg:DataProcessorObject.<Имя>`; тогда `DataPath` пишется как `Объект.Реквизит` и `Объект.ТабЧасть.Колонка`. Кнопки — явные `<Button>` с `<CommandName>Form.Command.Имя</CommandName>` внутри `AutoCommandBar` (см. ловушку про «Все действия» ниже), команды — `<Command name="Имя">` с `<Action>ПроцедураМодуляФормы</Action>`.

Дешёвая проверка перед загрузкой: сверить скриптом, что каждому `<Command>` соответствует кнопка и клиентская процедура `Процедура Имя(Команда)` в модуле формы, а каждый `DataPath` — реально существующий реквизит или колонка табличной части в XML объекта.

Реквизиты объектов добавляются правкой `<Тип>/<Имя>.xml`: скопировать блок `<Attribute>`, новый uuid через `[guid]::NewGuid()`.

## Наименования номенклатуры по шаблонам

Генерация имени вынесена из модуля формы в `Catalogs/Номенклатура/Ext/ManagerModule.bsl` — `СформироватьНаименованияПоШаблону(Объект)` возвращает структуру `(База, Укр, Рус, Предупреждения)` и **ничего не пишет**. Если для вида номенклатуры шаблона нет, возвращает `Неопределено` и вызывающий код работает по-старому (`ЗаполнитьНаименование()` в модуле формы элемента).

Шаблоны — данные, справочник `ШаблоныНаименований` (реквизиты `ВидНоменклатуры`, `Шаблон`). Своих форм у него нет намеренно: платформа рисует автоформу, править шаблоны можно без Конфигуратора.

Синтаксис:

| | |
|---|---|
| `[Реквизит]` | значение реквизита объекта |
| `[Реквизит=Зн1;Зн2]` | подставить, только если значение совпадает с одним из перечисленных |
| `[Реквизит!Зн1;Зн2]` | подставить, только если НЕ совпадает |
| `\|` | разделитель полей: поле, все токены которого пустые, выбрасывается **вместе со своими литералами**; оставшиеся склеиваются через ` \| ` |
| `( … )` | группа: если внутри не осталось ни одного поля, скобки не выводятся |

Литералы вне токенов сохраняются (` мм.`, `Ключ `, `DIA `, `/`). Первая буква имени и первая буква каждого поля в скобках → ВРег. Разбор идёт **по шаблону, а не по готовой строке**, поэтому `(`, `)`, `|` внутри значений реквизитов ничего не ломают.

Приём с регистром вместо условий: в шаблоне зарядных станций голова написана строчными — `[БП_ТипЗС] зарядная станция […]`. Пусто → «Зарядная станция …», заполнено → «Портативна зарядна станція …». Финальный ВРег доводит первую букву.

**Перевод укр↔рус ломался бы на новом формате.** `ПеревестиНаименованиеЧерезСоответствия` ищет слово по якорям (пробел с двух сторон, начало/конец строки). В формате со скобками первый токен стоит сразу после `(`, последний — перед `)`, ни один якорь не срабатывает, слово молча остаётся непереведённым. Лечится `ПеревестиНаименованиеПоФрагментам` — режет имя по `(`, `)`, `|` и переводит каждый фрагмент отдельно, так что границы полей становятся границами строки. Использовать **только его**; прямые вызовы старой функции на именах нового формата — баг.

**Перевод берётся из справочников соответствий, и направление важно.** Пар два: рус.→укр. — `БП_СоответствиеРуУкрСлов` (заполнен на 8 видов, там же масла), укр.→рус. — `БП_СоответствиеУкрРуСлов` (3 вида). Исходный код вычислял имя справочника по направлению в переменную `руНаУкрТекст` и **нигде её не использовал**: запрос в обе стороны жёстко читал `БП_СоответствиеУкрРуСлов`, то есть рус.→укр. справочник не участвовал в переводе вообще. `ПолучитьСловарьПереводов(ВидНоменклатуры, руНаУкр)` теперь читает нужный справочник, а если по этому направлению для вида пусто — откатывается на встречный (пары в обоих одинаковы по смыслу, колонки `СловоУкр`/`СловоРу`), чтобы не потерять переводы видов, заведённых только в одном из них.

**Целое поле переводится как словарная статья.** Значения токенов — это элементы справочников (`Полусинтетическое` из `БП_ТипОснованияМасла`), а в словаре слово заведено в старом виде — `(полусинтетическое)`, со скобками и строчной буквой. Ни один якорь такое не ловит. Поэтому `ПеревестиФрагментЦеликом` сначала сравнивает фрагмент целиком: словарные статьи при чтении нормализуются (`СнятьОбрамляющиеСкобки`), сравнение без учёта регистра, регистр первой буквы берётся от наименования, а не от словаря. Не совпало — работают старые правила подстроки. Никаких реквизитов в справочники-источники добавлять не нужно.

**Статьи словаря применяются от длинных к коротким.** Каждая статья работает по строке независимо, поэтому короткая, оказавшаяся выше по табличной части, съедает начало длинной: `Масло` → `Олива` превращает «Масло моторное» в «Олива моторное», и статья «Масло моторное» себя уже не находит — половина фразы остаётся русской. `УпорядочитьСловарьОтДлинныхСтатей` сортирует словарь по длине статьи при чтении, так что порядок строк в справочнике ни на что не влияет и короткие слова можно заводить безопасно.

У старой функции появился 4-й параметр `Словарь`: при пакетной обработке словари читаются один раз через `ПолучитьСловариПереводов(ВидНоменклатуры)` — это структура `(РуУкр, УкрРу)` с обоими направлениями, иначе запрос уходит на каждый фрагмент каждого имени. `ПеревестиНаименованиеЧерезСоответствия` принимает и структуру, и одну таблицу, и `Неопределено`.

**Резьба нормализуется при подстановке.** `НормализоватьРезьбу` приводит `12*1,5`, `12х1.5`, `12 X 1.5`, `М12х1.5` к единому `12x1,5`. Причина: в справочнике резьбы живут все три написания сразу, а в словаре `БП_СоответствиеУкрРуСлов` кто-то завёл пары вида «`14*1,5` → `14x1,5`» — из-за этого украинский и русский варианты одного имени расходились между собой. Нормализация срабатывает **только если всё значение реквизита целиком — это резьба** (`диаметр` + один разделитель + `шаг`); иначе легко испортить модель или артикул, где те же символы значат другое: `382/M-2CH`, `AG5/E23-2CH`, `416444x2`, `1/2"`. Проверено тестами на всех этих случаях.

`ПроверитьНаименования(Укр, Рус, Предупреждения)` — детекторы того, что платформа не покажет: длина против `Метаданные.Справочники.Номенклатура.ДлинаНаименования`, остатки `ы/ъ/э/ё` в украинском варианте и `і/ї/є/ґ` в русском (слова нет в словаре), `|` внутри значения реквизита, неизвестный реквизит в шаблоне.

Генерация идёт **от реквизитов, а не от текущего имени** — повторный прогон идемпотентен. Старая обработка `БП_ПереводНаименованийНоменклатурыПоСоответствию` работает от текущего имени, поэтому её повторный запуск данные портит.

### Пакетная перегенерация

Обработка `ПерегенерацияНаименований` (управляемая форма) — тонкая обвязка над модулем менеджера: `ПодготовитьПерегенерациюНаименований` (предпросмотр, ничего не пишет), `ЗаписатьПерегенерированныеНаименования`, `ОткатитьНаименования`. Предыдущие имена уходят в регистр `ИсторияНаименованийНоменклатуры`; откат берёт последнюю запись и **удаляет** её, поэтому повторный откат шагает по истории дальше назад.

Предпросмотр тянет значения реквизитов **одним запросом**, список полей которого строится из токенов шаблона (`ИменаРеквизитовШаблона`) — без `ПолучитьОбъект()` на строку. Служебные псевдонимы запроса намеренно называются `ПерегенСсылка`/`ПерегенКод`/`ПерегенБылоУкр`/`ПерегенБылоРус`, чтобы не столкнуться с именем реквизита из шаблона.

Запись идёт с `ОбменДанными.Загрузка = Истина` — иначе подписка Magento на каждую позицию пускает фоновое задание с фиксированным ключом и валится (см. ловушки). Регистрация в плане обмена «Сайт», которую при этом теряет `ПриЗаписи`, делается явно в `ЗарегистрироватьИзмененияДляСайта`; выгрузка — один раз пачками через `БП_ОбменMagentoВФоне.ВыгрузитьМассивНоменклатурыНаСайт`. Побочный эффект: пропускается блок проверок объекта из `ПередЗаписью` (единицы измерения и т. п.) — для операции «только переименование» это осознанно.

Строки, у которых новое имя длиннее `ДлинаНаименования`, **не записываются вовсе** и попадают в список ошибок: платформа обрезала бы имя молча.

## Оплата заказа и загрузка выписок

**Работает:** эквайринг WayForPay. Форма `ЗаказПокупателя.ФормаДокумента` (двоичная, но модуль читается) создаёт инвойс через `Wayforpay_ОбщийМодуль_СД` с настройками из `Подразделение.Настройка_WayforpayСД`, проверяет статус (`Approved`) и зовёт `Документы.ПлатежноеПоручениеВходящее.СоздатьПлатежПоЗаказу`. Организация, подразделение, контрагент, договор, валюта и НДС — из заказа, дедуп — по паре «заказ + `WayForPay_AuthCode`».

Модуль менеджера ППВ **самостоятелен**: от `БанковскиеВыписки` не зависит, поиск платежа по `НомерВходящегоДокумента` живёт у него же (`НайтиПоНомеруВходящегоДокумента`). Зависимость только в одну сторону — выписки зовут менеджер, не наоборот.

**Источник `WayForPay`** — выписка эквайринга: `БанковскиеВыписки.ПолучитьОперацииWayForPay` зовёт `Wayforpay_ОбщийМодуль_СД.ПолучитьСписокТранзакций` (метод API `TRANSACTION_LIST`) теми же реквизитами продавца, что и создание инвойсов. **Своих токена и айди не требует** — берётся `Подразделение.Настройка_WayforpayСД`. Дедуп двойной: платёж, заведённый кнопкой «Получить оплату» из заказа, ищется по паре «заказ + `WayForPay_AuthCode`», остальное — по `НомерВходящегоДокумента` (= `orderReference`). Заказ определяется по `orderReference` — это `<номер заказа>_<номер инвойса>`.

**Настраивается:** загрузка выписок Приват24 Бизнес / Monobank. Настройки — реквизиты `Подразделения` (`ИсточникБанковскойВыписки`, `ТокенБанковскойВыписки`, `АйдиБанковскойВыписки`, `ЗагружатьБанковскуюВыписку`, `НаправлениеОперацийВыписки`, `БанковскийСчетВыписки`), но **редактируются они в самой обработке**: `ФормаЭлемента` подразделения — двоичная, новые реквизиты на неё не попадают, а лезть в Конфигуратор ради этого не нужно. Внизу формы обработки — таблица «Настройки загрузки по подразделениям» и кнопки «Записать настройки» / «Перечитать настройки».

`id` и `token` берутся в кабинете банка (у Привата — «Автоклиент», у Monobank — токен разработчика плюс id счёта из `/personal/client-info`). Учётка WayForPay сюда не подходит: это другой сервис, `api.wayforpay.com` против `acp.privatbank.ua` / `api.monobank.ua`.

Расписание регламента `ЗагрузкаПриват24` задаётся в базе, до проверки он стоит с `Использование = false`. После подтверждения — включить и выключить отладку `БанковскиеВыписки.ВключенаОтладкаБанковскихВыписок`.

В модуле `Wayforpay_ОбщийМодуль_СД` из чужого кода тронута **одна** функция — `СоздатьИнвойс` (запрет эквайринга, см. ниже); остальное только дописано: `ПолучитьСписокТранзакций`, `OrderReference*`, `ЗаписатьЗаказИнвойса`.

### Формы расчёта, по которым инвойс не выставляется

Наложенный платёж деньги берёт при выдаче, поэтому инвойс WayForPay по такому заказу — вторая оплата того же заказа. Запрет живёт в `Wayforpay_ОбщийМодуль_СД`: `КодыФормРасчетаБезЭквайринга()` (список кодов через запятую, сейчас `000000005` — «Нова Пошта (наложений платіж NovaPay)»), `ЭквайрингЗапрещен(ФормаРасчета)`, `ТекстЗапретаЭквайринга(ФормаРасчета)`. Опознаём **по коду**: предопределённых элементов `ФормыРасчета` для этих форм нет, а наименование правят руками.

Проверок три, потому что у создания инвойса три входа:

* `Wayforpay_ОбщийМодуль_СД.СоздатьИнвойс` — последний рубеж перед вызовом API, через него идут все, в том числе обе кнопки формы заказа. Отказ доезжает до формы заказа как `Рез.Сообщение` (`Сообщить`), но счётчик `КоличествоИнвойсов_Wayforpay` там всё равно увеличивается — так написан типовой обработчик, а его код лежит в двоичной форме;
* `СенсорныйЕкран_Оплата_СД.СоздатьИнвойс` — отказ **до** записи заказа, без роста счётчика;
* `Форма_Оплата.ПерейтиКБезналу` (терминал) — плитка «Безнал» на таком заказе не открывает экран безнала вовсе: иначе `ВыбратьБезналичнуюФормуРасчета` молча сменила бы форму расчёта на безналичную, и запрет перестал бы срабатывать.

Добавить ещё одну форму расчёта — дописать её код в `КодыФормРасчетаБезЭквайринга`.

## Именование новых объектов

Префикс `БП_` — неймспейс предыдущего подрядчика, для новых объектов **не используем**. Существующие `БП_*` (`БП_НаименованиеРу`, `БП_ОбменMagento`, `БП_СоответствиеУкрРуСлов`, …) не переименовываем: это чужой код с сотнями точек вызова, выгода нулевая, риск реальный.

## Ловушки платформы — проверять сразу

* **Строковые реквизиты и колонки ТЗ молча усекают значение.** Колонка `Строка(15)` примет длинный идентификатор и обрежет его — без ошибки. Если по этому значению потом ищут документ, дедуп ломается. Правило: ключ поиска строить из фактически сохранённого значения, а не из исходного.
* **Фоновое задание, запущенное из `ПриЗаписи`, работает в незафиксированной транзакции** — отдельный сеанс либо не видит документ вообще, либо читает старое состояние. Лечится очередью: `ПриЗаписи` только регистрирует объект в регистре сведений (в той же транзакции), разгребает регламентное задание. Плюс: ключ фонового задания = GUID объекта → повторный запуск при занятом ключе молча отбрасывается.
* **Расписание предопределённых регламентных заданий в метаданных не хранится** — после загрузки конфигурации его нужно задать в базе. Иначе очередь копится, и это не даёт никакой ошибки.
* **`Попытка … Исключение Возврат`** в типовом коде глотает реальные баги. Если «функция просто ничего не делает» — искать такой блок.
* **У управляемых форм в старых конфигурациях команды могут не попадать в «Все действия»** — кнопки приходится размещать явным `CommandBar` в `Form.xml`, иначе форма открывается вообще без кнопок.
* **`ОбменДанными.Загрузка` в проверках часто инертен** — если конфигурация не узел плана обмена, флаг никто не выставляет.
* **Внедрённые ActiveX-объекты в макетах калечатся выгрузкой в файлы.** Штрихкод в печатной форме — не картинка, а объект (`<drawingType>Object</drawingType>` в `Template.xml`); выгрузка может потерять блоб `<object>` и/или `namedItem` рисунка, и заливка такого файла снесёт объект уже в базе — останется пустая рамка. Обычные картинки (`drawingType=Picture`) не страдают. В этой базе такой макет один: `CommonTemplates\Этикетка\Ext\Template.xml` — после каждой выгрузки из Конфигуратора и **до** заливки проверять, что `<object>` и `namedItem` на месте (скриптов `fix/check-barcodes.ps1` из пакета «Перенос_ШтрихкодыВМакетах» здесь нет — при необходимости перенести). Компонента «1С:Печать штрихкодов» 32-битная — из 64-битного клиента недоступна в принципе.
* **Посторонних `.xml` внутри папки выгрузки быть не должно.** «Загрузить конфигурацию из файлов» парсит каждый `.xml` в дереве, включая служебные. Эталон штрихкода лежал как `_tools/barcode-object.xml` и валил загрузку: «Помилка розбору XML — Namespace prefix xsi for type on object is not defined» (это фрагмент, без объявления `xsi`). Переименован в `_tools/barcode-object.txt`. Файлы других типов (`.ps1`, `.md`, `.gitignore`) Конфигуратор не трогает.
* **В `Template.xml` строки продолжения base64 обязаны начинаться с нулевой позиции** — любой отступ внутри блока даёт при загрузке «Ошибка формата потока». После правки макета проверять XML валидатором (`XmlDocument.Load`).
* **Выгрузка на сайт стартует с фиксированным ключом фонового задания.** `БП_ОбменMagento.MagentoПередЗаписьюНоменклатурыПередЗаписью` на каждую запись номенклатуры делает `ФоновыеЗадания.Выполнить(…, "MagentoID")` / `"MagentoGarazhID"` — ключ один на всю базу, а не GUID объекта. При массовой перезаписи задания конфликтуют по ключу и часть выгрузок теряется молча. Массовые прогоны писать в обход подписки.
* **Путей выгрузки номенклатуры три, и они шлют разное.** Выбирать по тому, что нужно отправить:

  | функция | endpoint | шлёт `name` | кто зовёт |
  |---|---|---|---|
  | `MagentoВыгрузкаНоменклатуры` | `PUT /erp/products/safe-update/<Код>` (нет `MagentoID` → `POST /erp/products`) | да | подписка при записи объекта |
  | `MagentoМасоваяВыгрузкаНоменклатуры` | `POST /erp/products/safe-update-multiple/` | да, плюс `i18n` (`ua` = `Наименование`, `ru` = `БП_НаименованиеРу`) | **никто** — мёртвый код, и отправки внутри нет, функция только собирает структуру |
  | `MagentoМасоваяВыгрузкаНоменклатурыДляАсинхронойОтправки` | `PUT /erp/products/stock-multiple-async/<request_id>` (через `УстановкаЦенНоменклатуриОтправить`) | **нет, строка закомментирована** | `БП_ОбменMagentoВФоне.ВыгрузитьМассивНоменклатурыНаСайт` |

  Отсюда грабли: пакетная выгрузка отправляет цену, остаток, бейджики и атрибуты, но **не наименование** — после переименования имя на сайте остаётся старым, а операция при этом рапортует об успехе. Для имени годится только `MagentoВыгрузкаНоменклатуры` (по одной позиции). Так и сделано в `ЦВ_ПерегенерацияНаименований.ВыгрузитьМассивНаСайт`.
* **В ветке создания карточки подписка передаёт ссылку там, где нужен объект.** `MagentoПередЗаписьюНоменклатурыПередЗаписью` кладёт в фоновое задание `Источник.ссылка`, а `MagentoВыгрузкаНоменклатуры` при пустом `MagentoID` после `POST /erp/products` делает `Источник[MagentoID] = Данные.magento_id` — записать реквизит у ссылки нельзя. По коду выходит, что для новой номенклатуры карточка на сайте создаётся, а выданный `magento_id` не сохраняется. Проверено только чтением кода, в журнале регистрации не смотрели. Свой код, который зовёт эту функцию напрямую, должен передавать объект и сам записывать его, если `MagentoID` появился (`ЦВ_ПерегенерацияНаименований.ВыгрузитьПозициюНаСайт`).

## Типовой профиль оптимизации

Тормоза в формах подбора/списков почти всегда — **N+1 в построчных обработчиках**: `ПриВыводеСтроки` и `ПриАктивизацииСтроки` дёргают функции с собственными запросами (остатки, резервы, цвета, характеристики) на каждую строку и на каждую перерисовку, без кэша. Лечение по порядку:

1. кэш в переменных формы на время открытого диалога (обёртки над теми же функциями);
2. один пакетный запрос (`Запрос.ВыполнитьПакет`) на прогрев кэша сразу по всем строкам вместо цикла;
3. тяжёлую разовую работу из `ПриОткрытии` вынести в `ПодключитьОбработчикОжидания(…, 0.1, Истина)` — диалог показывается мгновенно (трейд-офф проговорить с пользователем).

## Среда

Работаю на **macOS, PowerShell 7 (`pwsh`)**; машина с 1С — **Windows Server 2022, Windows PowerShell 5.1**.
Скрипты должны оставаться рабочими в обеих средах, поэтому писать их по правилам 5.1:

* `.ps1` с кириллицей сохранять в **UTF-8 с BOM**, иначе парсер ломается на первой же кириллической строке. Инструмент Write пишет без BOM — дописывать через `[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding $true))`.
* Нет `&&` / `||`, тернарника и `??`. Вместо `head`/`tail` — `Get-Content -TotalCount` / `-Tail`.
* Кириллицу в коде не передавать через `powershell -Command "..."` — двойные кавычки съедают `$_` и ломают вложенный код; скрипты запускать через `-File`.

## Как работать

* Для поиска по коду — **Grep одним вызовом**, не циклы в шелле: каждый вызов шелла дёргает подтверждение прав и это раздражает.
* Не проверять то, что и так почти наверняка верно (уникальность свежесгенерированного GUID и т. п.).
* Формы, чей код есть только в скомпилированном `Form.bin` у сторонних подсистем, — не читаются; поведение приходится выводить из модулей объектов. Это проговаривать, а не выдавать догадку за факт.
